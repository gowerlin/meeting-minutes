S1｜好，時間差不多了，我們開始上課。各位好，我是高志遠，今天是「資料庫效能調校」系列課程的第一堂，主題是索引與查詢效能。今天的課大概分成四個部分：第一，為什麼查詢會變慢；第二，B-tree 索引的原理；第三，複合索引怎麼設計；第四，建索引的代價。最後會用一個實際的案例，把前面的東西串起來。
S1｜先講一下上課的方式。投影片會在課後放到內部的學習平台，所以大家不用急著抄。中間有任何問題可以直接舉手，不用等到最後。另外，今天最後會出一個小作業，下週三之前交。
S1｜<3.5>好，第一個部分，為什麼查詢會變慢。我先問大家一個問題：一張有五百萬筆資料的訂單表，你要找某一個客戶的訂單，資料庫要怎麼找？／如果什麼都沒有準備，它只能從第一筆看到最後一筆，這個叫做全表掃描，英文是 full table scan。
S1｜全表掃描本身不是壞事。表很小的時候，例如只有幾百筆的設定表，全表掃描反而最快，因為整張表可能就在一兩個資料頁裡面。問題是表變大以後，掃描的成本跟資料量成正比，五百萬筆就要看五百萬筆。
S1｜那我們怎麼知道資料庫實際上是怎麼找的？這就要看執行計畫。在 PostgreSQL 裡面，你在查詢前面加上 EXPLAIN，它就會告訴你它打算怎麼執行；加上 EXPLAIN ANALYZE，它會真的跑一次，然後告訴你每一步實際花了多少時間、處理了多少筆。
S1｜看執行計畫的時候，我建議大家先看三個地方。第一，有沒有出現 Seq Scan，也就是全表掃描；第二，估計的筆數跟實際的筆數差多少，差很多通常表示統計資訊過期了；第三，哪一個節點花的時間最多，／先處理最花時間的那一步。
S1｜統計資訊這件事很多人會忽略。資料庫是根據統計資訊，來估計每一步會回傳多少筆，再決定要不要用索引。如果你剛剛匯入了一大批資料，統計資訊還是舊的，它就可能做出錯誤的選擇。這時候跑一次 ANALYZE，讓它重新收集統計資訊，常常就會好很多。
S1｜還有一個常見的情況，是查詢本身寫法的問題。例如在欄位外面包了一個函數，像是把建立時間轉成日期再比較，這樣一般的索引就用不到了，因為索引裡面存的是原本的值，不是函數算完的結果。
S1｜類似的還有隱含的型別轉換。欄位是文字，你拿數字去比，資料庫可能會把每一筆都轉型之後再比，索引一樣失效。所以看到執行計畫裡面明明有索引卻沒有用，先檢查條件的兩邊型別是不是一致。
S1｜<2.8>好，接下來第二部分，B-tree 索引。大家可以把索引想成書最後面的索引頁。你要找「交易隔離」這個詞，不用從第一頁翻，先翻到索引頁，找到這個詞在第幾頁，再直接翻過去。
S1｜B-tree 是一種平衡的樹狀結構。最上面是根節點，中間是分支節點，最下面是葉節點。葉節點裡面存的是排好序的鍵值，還有指向實際資料列的位置。因為它是平衡的，所以不管你找哪一個值，從根走到葉的步數都一樣，通常三到四層就可以涵蓋幾千萬筆資料。
S1｜這裡有一個重點：B-tree 裡面的資料是排好序的。所以它不只能做等於的查詢，也能做範圍查詢，例如日期在某一天到某一天之間；還能幫忙排序，例如依建立時間排序，如果剛好有這個欄位的索引，資料庫就可以直接照索引的順序讀，不用另外排序。
S1｜那索引找到以後，還要回到表裡面去拿其他欄位，這一步叫做回表。如果你要的欄位全部都在索引裡面，就不用回表，這種情況叫做覆蓋索引，在 PostgreSQL 的執行計畫裡面會看到 Index Only Scan。
S2｜老師，我想問一下，那是不是索引建越多越好？反正查詢都會變快。
S1｜好問題，這個剛好是我們第四部分要講的，我先簡單回答：不是。索引不是免費的，每多一個索引，寫入的時候就多一份要維護的資料。這個我們等一下講代價的時候再詳細說。
S1｜<3.2>好，第三部分，複合索引。複合索引就是一個索引裡面包含好幾個欄位，例如客戶編號加上訂單日期。它的排序方式是先依第一個欄位排，第一個欄位一樣的，再依第二個欄位排，就像電話簿先依姓氏、再依名字排一樣。
S1｜所以複合索引有一個很重要的規則，叫做最左前綴原則。如果索引是客戶編號加訂單日期，你的查詢條件有客戶編號，就可以用到這個索引；有客戶編號加訂單日期，也可以；但是如果你只用訂單日期查，通常就用不到，因為訂單日期在索引裡面不是照順序排的。
S2｜那複合索引的欄位順序要怎麼決定？是把區分度高的放前面嗎？
S1｜這個問題很常見。區分度是一個參考，但不是唯一的標準。我的建議是先看查詢條件：用等於比較的欄位放前面，用範圍比較的欄位放後面。例如「某個客戶、某段日期」，客戶編號是等於，日期是範圍，那就是客戶編號在前、日期在後。
S1｜為什麼範圍要放後面？因為範圍條件之後的欄位，在索引裡面就不再是連續排好的了。你把日期放前面、客戶放後面，資料庫在日期範圍裡面還是要一筆一筆檢查客戶編號，效果就差很多。區分度是在這個前提之下，再拿來比較兩個都是等於條件的欄位。
S1｜另外補充兩種比較進階的索引。第一種是部分索引，只替符合條件的資料建索引，例如只替還沒出貨的訂單建，因為大部分的查詢只看還沒出貨的那一小部分，索引就會小很多。第二種是運算式索引，剛剛說在欄位外面包函數會讓索引失效，那就直接替函數的結果建索引。
S3｜老師，那如果查詢用的是 LIKE，例如名稱前面有一個百分比，這樣還能用到索引嗎？
S1｜如果百分比在前面，例如找名稱裡面「包含」某個字，一般的 B-tree 索引就用不到了，因為它不知道要從哪裡開始找。如果是開頭相同，例如名稱「以」某個字開頭，那就可以用。
S1｜真的需要做包含的搜尋，PostgreSQL 可以用 pg_trgm 這個擴充套件，建 GIN 索引，它是把字串切成三個字元一組來建索引。資料量再大一點、要做全文檢索的，就要考慮專門的搜尋引擎了。不過中文的斷詞是另外一個題目，今天先不談。
S1｜<4.0>好，第四部分，索引的代價。剛剛詩涵問索引是不是越多越好，我們現在來看代價。第一個是寫入成本：每一次新增、修改、刪除，資料庫除了改表，還要改每一個相關的索引。一張表有十個索引，寫入一筆資料，背後可能是十幾次的寫入。
S1｜第二個是空間。索引本身也要佔磁碟，有些大表的索引加起來比資料本身還大。空間大了，記憶體裡面能放的資料頁就少了，快取命中率下降，反而會讓其他查詢變慢。
S1｜第三個是維護成本。PostgreSQL 的索引在大量更新以後會膨脹，需要定期整理；索引多了，備份和還原的時間也會變長。所以我的原則是：每一個索引都要說得出是為了哪幾支查詢建的。說不出來的，就要考慮拿掉。
S1｜那要怎麼找出沒有在用的索引？PostgreSQL 有一個統計檢視表叫 pg_stat_user_indexes，裡面有每個索引被使用的次數。觀察一段時間，例如一個月，使用次數是零的索引，就是候選。不過要注意，有些索引是為了月底結帳或年度報表才用的，觀察的期間要涵蓋這些情況。
S2｜老師，那我們在線上的資料庫直接建索引，會不會鎖住整張表？我們的訂單表白天一直有人在寫。
S1｜這個要看資料庫。在 PostgreSQL，一般的 CREATE INDEX 會擋住寫入，所以線上環境要用 CREATE INDEX CONCURRENTLY，它不會擋寫入，代價是建得比較慢，而且如果中途失敗，會留下一個無效的索引，要手動刪掉再重建。
S1｜至於我們公司另一套系統用的 MySQL，線上建索引要看版本跟儲存引擎，我印象中我們那個版本是支援的，但是我不想在這邊給大家錯的答案。這個我回去跟 DBA 確認之後，再公告在學習平台上。
S1｜<3.0>好，最後我們用一個實際的案例，把今天講的東西串起來。這是去年我們客服系統的一個查詢：客服人員輸入客戶編號，要列出這個客戶最近九十天的訂單，依建立時間由新到舊排，一頁顯示二十筆。當時這個查詢平均要三點二秒，尖峰的時候甚至會超過十秒。
S1｜我們先跑 EXPLAIN ANALYZE，發現它用了一個只有建立時間的索引，從最新的訂單往回一筆一筆找，找到屬於這個客戶的才留下來。這個客戶如果訂單很少，就要往回掃非常多筆，才湊得滿二十筆。
S1｜解法是建一個客戶編號加建立時間的複合索引。客戶編號是等於條件放前面，建立時間放後面，同時也剛好滿足排序。建好以後，資料庫直接跳到這個客戶的那一段，照時間順序讀二十筆就結束了。查詢時間從三點二秒降到大約四十毫秒。
S1｜然後我們順便檢查了這張表原本的索引，總共有十一個，其中三個在過去兩個月使用次數是零，跟業務單位確認以後拿掉了兩個，另一個是年度報表要用的，保留下來。寫入的平均延遲也因此降了大約百分之十五。
S1｜這個案例有兩個重點。第一，先看執行計畫再動手，不要用猜的；第二，加索引的同時，也要檢查有沒有該拿掉的索引。
S1｜<2.5>好，今天的內容差不多到這裡，我整理一下重點：第一，慢查詢先看執行計畫，注意全表掃描和估計筆數；第二，B-tree 是排好序的，能做等於、範圍和排序；第三，複合索引遵守最左前綴，等於條件在前、範圍條件在後；第四，索引有寫入、空間和維護的代價，每一個索引都要說得出理由。
S1｜作業的部分：請大家從自己負責的系統裡，找出最慢的三支查詢，跑 EXPLAIN ANALYZE，把執行計畫貼到學習平台的共用文件，並且寫一兩句你覺得慢在哪裡。下週三之前交，下次上課我們挑幾個來一起看。
